1. THE PROBLEM WITH THE ORIGINAL REPORT
========================================

The original CSV file exported from Finite State contained 2,695 CVE
findings across 21 columns. While it included severity, CVSS scores,
CWE identifiers, reachability status, and NVD links, it had a critical
usability gap: the "Component" column (column I) was far too generic.

For example, for CVE-2019-18805 the component was listed simply as
"Linux" with version "4.9.152". This tells you nothing about WHERE in
the Linux kernel the vulnerability actually exists. The kernel has over
30 million lines of code across thousands of subsystems. Telling an
engineering team "you have a vulnerability in Linux" is not actionable.

The actual affected location for that CVE is net/ipv4/sysctl_net_ipv4.c,
specifically in the tcp_ack_update_rtt() function within the IPv4
networking subsystem. That information was buried inside the free-text
Description column (column Q), making it impossible to sort, filter,
group, or assign work based on it.

The same problem applied to the vast majority of the 2,695 CVEs in
the report. The result was that the report, while comprehensive in
volume, was practically unusable for triage, prioritization, or
assignment to specific engineering teams.


2. WHAT WE DID TO FIX IT
=========================

We applied a three-phase enrichment process, each building on the
previous one, to extract and add structured, actionable data to every
CVE row.


PHASE 1: Regex-Based Extraction from Descriptions
--------------------------------------------------
Script: extract_cve_details.py

We wrote a Python script that parsed the Description column (Q) of
every CVE row using regular expressions to extract:

  - Affected File/Path: Source code file paths mentioned in the
    description (patterns like "net/ipv4/sysctl_net_ipv4.c" or
    "drivers/media/usb/dvb-usb/technisat-usb2.c").

  - Affected Function(s): Function names mentioned in the description
    (patterns like "tcp_ack_update_rtt()" or "aa_label_parse()").

  - Affected Subsystem: A human-readable classification derived from
    the file path or description keywords. For example, a file under
    "drivers/net/wireless/marvell/" maps to "WiFi Driver / Marvell",
    and a file under "net/ipv4/" maps to "Networking / IPv4".

The subsystem classification uses a mapping table of over 50 kernel
directory prefixes to readable names, with a keyword-based fallback
for descriptions that mention subsystem names without file paths.

Results after Phase 1:
  - Affected File/Path:  991 out of 2,695 (37%)
  - Affected Function:  1,205 out of 2,695 (45%)
  - Affected Subsystem: 1,664 out of 2,695 (62%)

This was a significant improvement but still left 1,704 CVEs without
a file path, because many NVD descriptions are vague and do not
mention specific source files.


PHASE 2: NVD API and Git Kernel Patch Lookups
----------------------------------------------
Script: nvd_enrich.py

For the 1,704 CVEs still missing file paths, we queried the NIST
National Vulnerability Database (NVD) API v2.0 to retrieve the full
list of references for each CVE. These references often include
direct links to git commit patches on git.kernel.org or github.com.

For each CVE with a git commit reference, the script:

  1. Called the NVD API at services.nvd.nist.gov/rest/json/cves/2.0
     to get the reference URLs for that CVE.

  2. Identified git commit URLs (git.kernel.org/stable/c/...,
     git.kernel.org/.../commit/?id=..., or github.com/.../commit/...).

  3. Fetched the actual git patch (the diff) from those commit URLs.

  4. Parsed the "diff --git a/path b/path" lines from the patch to
     extract the exact source files that were modified in the fix.

  5. Updated the Affected File/Path, Function, and Subsystem columns
     with the extracted data.

The script included rate limiting (6.5 seconds between NVD API calls
to stay within the public rate limit of 5 requests per 30 seconds),
automatic checkpointing every 50 CVEs to avoid data loss, and retry
logic for transient failures.

Special handling was added for the git.kernel.org/stable/c/<hash>
URL format, which required conversion to the /patch/?id=<hash> format
to retrieve the raw diff.

Results after Phase 2:
  - Affected File/Path:  2,509 out of 2,695 (93%)
  - Affected Function:   1,205 out of 2,695 (45%)
  - Affected Subsystem:  2,538 out of 2,695 (94%)

This filled in 1,516 additional CVEs. The remaining 186 CVEs had no
git commit URLs in their NVD references (their references only pointed
to advisory pages like Red Hat, Ubuntu, Debian, or OpenWall).


PHASE 3: Linux Kernel CVE Tracker Database and Known Mappings
--------------------------------------------------------------
Script: kernel_cve_enrich.py

For the final 186 orphan CVEs, we used two additional data sources:

A) Known Mappings for Non-Kernel Components

   For non-kernel CVEs (hostapd, wpa_supplicant, OpenWrt), the NVD
   references and kernel CVE tracker would not have relevant data.
   We created a curated mapping table based on the actual upstream
   fix commits for these projects. This covered 18 CVEs including:

     - CVE-2022-23304, CVE-2022-23303 (hostapd/wpa_supplicant SAE and
       EAP-PWD side-channel attacks)
     - CVE-2019-9494 through CVE-2019-9499 (WPA3 Dragonfly handshake
       vulnerabilities)
     - CVE-2020-28951 (OpenWrt libuci use-after-free)

B) Linux Kernel CVE Tracker (nluedtke/linux_kernel_cves)

   This is a community-maintained GitHub repository that maps kernel
   CVE IDs to their fix commit hashes. We downloaded the full database
   (3,324 kernel CVEs) and cross-referenced it with our 168 remaining
   orphan CVEs. For each match, we:

     1. Retrieved the fix commit hash from the database.
     2. Fetched the actual patch from git.kernel.org using that hash.
     3. Extracted the changed file paths from the diff.
     4. Derived the subsystem classification from those file paths.

   This successfully filled in 137 additional CVEs.

Results after Phase 3:
  - Affected File/Path:  2,664 out of 2,695 (98%)
  - Affected Function:   1,282 out of 2,695 (48%)
  - Affected Subsystem:  2,621 out of 2,695 (97%)

Only 31 CVEs remain without a file path. These are CVEs with no
public fix commits in any database we checked. 17 CVEs have all
three enriched fields empty.


3. EXCEL FORMATTING AND USABILITY IMPROVEMENTS
================================================
Script: create_excel_report.py

The enriched CSV was converted to a formatted Excel workbook with
the following visual and functional improvements:

A) Column Reordering

   The three new columns were moved from the end of the sheet
   (columns V, W, X) to immediately after the Severity column
   (columns C, D, E). This ensures the most actionable information
   is visible immediately without horizontal scrolling.

   New column order for the first columns:
     A = CVE ID
     B = Severity
     C = Affected File/Path
     D = Affected Function(s)
     E = Affected Subsystem
     F = CVSS (and remaining original columns follow)

B) Color Coding

   Each of the three new columns has a distinct color to make them
   visually distinct and easy to scan:

     - Column C (Affected File/Path):    Azure/light blue background
     - Column D (Affected Function(s)):  Light green background
     - Column E (Affected Subsystem):    Light orange background

   The headers for these columns use darker versions of the same
   colors (dark blue, dark green, dark orange) with white text.

   The Severity column (B) is also color coded:
     - Critical: Red background, white text
     - High:     Orange background, white text
     - Medium:   Yellow background, dark text
     - Low:      Green background, dark text

C) Dropdown Filters

   Two data validation dropdowns were added for quick filtering:

     - Severity column (B): Dropdown with values critical, high,
       medium, low. Allows quick selection to focus on specific
       severity levels.

     - Affected Subsystem column (E): Dropdown with 67 unique
       subsystem values (e.g., "Networking / IPv4", "WiFi Driver /
       Marvell", "Filesystem / Btrfs", etc.). Since the list exceeds
       Excel's 255-character inline limit, the values are stored on
       a hidden helper sheet named "_Subsystems".

D) Additional Formatting

     - Frozen header row: The top row stays visible while scrolling.
     - AutoFilter enabled on all columns for native Excel filtering.
     - Auto-fitted column widths (capped at 45 characters).
     - Thin borders on all cells for readability.
     - Text wrapping on header cells.

6. HOW TO USE FOR FUTURE SCANS
================================

When a new Finite State scan CSV is exported, run the scripts in order:

  1. python extract_cve_details.py <new_scan.csv>
  2. python nvd_enrich.py
  3. python kernel_cve_enrich.py
  4. python create_excel_report.py

The entire pipeline takes approximately 2-3 hours due to NVD API rate
limits (Phase 2). Phases 1, 3, and 4 complete in under a minute each.
